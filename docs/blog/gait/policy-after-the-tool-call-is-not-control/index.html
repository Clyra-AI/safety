By David Ahmann (LinkedIn)

If Policy Runs After the Tool Call, It Isn't a Control

This is the place where many AI governance programs quietly become decorative. The organization has policies. The prompt mentions those policies. Logs exist after the fact. But when the tool call actually happens, nothing at the boundary can stop it. That is not a control. That is a hope wrapped in process language.

Repo grounding

The Gait repo centers the boundary explicitly: evaluate structured tool-call intent with gait gate eval, return allow, block, or require_approval, and treat non-allow as non-execute.

The operational reality

Ask an AppSec lead whether an agent is allowed to touch a certain internal system and the answer often comes back in policy language: "it should not," "that workflow requires approval," "the agent was instructed not to do that." Those answers sound responsible until the obvious follow-up appears: what happens if the agent tries anyway?

If the system can still execute the action while policy gets enforced later in review, then the boundary is not where the policy lives. The policy lives in documentation, coaching, or retrospective judgment. That may still be useful, but it is not the same thing as an execution control.

The anti-pattern

The anti-pattern is advisory policy. Teams write excellent guidance, maybe even collect reviewer approvals, but the actual tool path stays live unless a human catches the issue in time. This is the same mistake earlier automation programs made when they confused runbooks and guardrails. One tells the system what should happen. The other changes what may happen.

Prompt rules are especially easy to overtrust here because they feel close to the model. But the model is not the boundary. The tool call is. By the time the action reaches a real system, the only question that matters is whether something outside the model can still say no.

The better system pattern

The better pattern is boundary-first policy. The agent expresses intent. A gate evaluates that intent against explicit rules. The runtime receives a verdict before the side effect executes. If the verdict is not allow, the action does not happen. That is the point where policy stops being commentary and becomes an operating control.

Gait is useful implementation context because the repo is explicit about that exact split. The policy is YAML. The decision happens at the tool boundary. The artifact trail survives the decision. Those are the right ingredients for a system that AppSec can evaluate without pretending the prompt itself is a sufficient fence.

This pattern also makes approvals much more honest. If a policy says an action requires approval, the runtime can hold it non-executable until approval exists. That looks much more like a protected environment than a polite note in a runbook.

Why security and the CISO care

Security leaders need this distinction because it changes how risk is priced. An advisory workflow can still be valuable, but it should not be reported upward as if it were a hard boundary. The CISO needs to know which controls can actually block unsafe execution and which ones merely help the team notice mistakes afterward.

That difference becomes brutal during incidents. If the only evidence of policy is a prompt, a wiki page, or a human expectation, the organization is left defending intent rather than describing an enforceable mechanism.

Why platform and engineering care

Platform teams benefit because explicit boundary verdicts reduce ambiguity. Instead of asking whether the agent "usually behaves" or whether reviewers "would probably catch it," the workflow has a clear decision point. That clarity makes automation more reusable and less political across teams.

It also improves debugging. When a step is blocked, a reviewer can see that it was blocked and why. That is much better than arguing over whether the model misunderstood an instruction.

Practical next step

  • Choose one write-capable action that currently depends on policy language or reviewer attention alone.
  • Move the control question to the tool boundary: can the runtime allow, block, or require approval before execution?
  • Record the verdict and reason code as a durable artifact instead of leaving the decision buried in logs.
  • Review which controls in your current program are truly blocking controls and which are advisory.
  • Report that difference upward honestly.

Once teams accept that policy has to run at the boundary, another common shortcut needs correcting too: the idea that this is just an ".eslintrc for agents."
