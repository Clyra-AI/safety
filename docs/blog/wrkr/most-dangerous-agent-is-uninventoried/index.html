The Most Dangerous AI Agent Is the One Security Never Inventoried

Most AppSec teams are not losing sleep because an agent became too intelligent. They are losing sleep because adoption has outpaced inventory. Someone enabled a coding assistant, installed an MCP server, added a workflow action, or wired a write-capable path into a repo, and nobody in security can say exactly where that path now exists or what it can touch.

Repo grounding

The current Wrkr repo is explicit about this layer of the problem: deterministic discovery across local setup, repositories, GitHub orgs, MCP declarations, and CI execution patterns, with machine-readable states such as approved, known_unapproved, and unknown_to_security.

The operational reality

A CISO asks a reasonable question: how many AI coding tools and agents are currently on write-capable paths in our delivery system? The room usually answers with fragments. Someone knows the official standard. Someone else knows what is allowed in CI. A platform lead knows what was piloted. A few engineers know what is really running on their machines. The organization has policies. It does not have one inventory.

That gap is what makes the unknown path dangerous. An agent that is already documented, scoped, and reviewed may still deserve controls, but at least it can enter a serious governance conversation. The unknown-to-security path is worse because it collapses three problems together: missing approval context, unclear privilege boundary, and no durable evidence trail if something goes wrong later.

This is also why the argument cannot stop at "developers are using AI tools." That observation is too broad to be useful. The question that matters is narrower and more operational: which of those tools can currently change code, mutate CI behavior, touch credentials, or inherit production reach through the systems around them?

The anti-pattern

The anti-pattern is treating AI tooling like a software-procurement list. Security keeps a rough catalog of approved products, engineering assumes that anything not explicitly blocked is low-risk, and the real execution surfaces spread underneath both groups. That might have been survivable when the tools only generated text. It breaks once those tools participate in software delivery.

The practical failure is not just incomplete coverage. It is false confidence. Leaders can say "we know our approved tools" while unknown-to-security paths already exist in skills directories, MCP config files, repository scaffolds, local IDE settings, or CI actions that nobody thinks of as agent infrastructure. The absence of a coherent inventory is what lets these paths become normal before they become visible.

The better system pattern

The better pattern starts with inventory as a control surface. Not a vanity dashboard. Not a once-a-year review. A deterministic answer to four questions: what exists, where it is declared, what it can touch, and how its approval status is represented. That is the point where a tool like Wrkr becomes useful implementation context. The important idea is not the brand. It is the shape of the output.

Good output for this problem is machine-readable and specific. It should separate local setup from repo-scoped declarations. It should identify CI execution patterns separately from interactive developer tooling. It should tell you whether a path is already write-capable or becomes effectively write-capable once it inherits access from the surrounding environment. And it should make "unknown to security" a first-class state instead of a fuzzy concern raised in meetings.

Once that structure exists, governance gets much less theatrical. AppSec can review something concrete. Platform can reduce ambiguity. Leadership can ask whether the unresolved inventory is shrinking over time rather than arguing abstractly about whether the organization is "good at AI governance."

Why security and the CISO care

Unknown inventory is expensive because it poisons every later control. Approval programs degrade into exceptions-by-memory. Audit prep turns into spreadsheet archaeology. Incident review begins with basic reconstruction rather than decision-making. Even strong teams end up answering executive questions with inference instead of evidence.

For a CISO, this is not just a tooling problem. It is a trust problem. If the organization cannot say where write-capable AI paths already exist, then every later assurance statement is weaker than it sounds. You cannot govern what you cannot enumerate.

Why platform and engineering care

Platform teams often feel the operational cost of missing inventory before security does. They are the ones untangling workflow drift, reconciling overlapping tool assumptions, and cleaning up local setup differences that only surface once CI behaves unexpectedly. A unified inventory helps because it turns hidden differences into visible inputs.

That is also the moment when discovery stops feeling bureaucratic. Good discovery reduces onboarding time, clarifies repo expectations, and makes later runtime control more precise because the organization finally knows which paths deserve attention first.

Practical next step

  • Pick one engineering group and enumerate every AI tool, agent, MCP server, and CI path currently involved in software delivery.
  • Separate local setup, repo declarations, and workflow execution into different inventory buckets.
  • Add an explicit state for paths security has never reviewed.
  • Mark which of those paths are write-capable now versus conditionally write-capable after environment inheritance.
  • Review whether that output is machine-readable enough to survive an audit or an incident six months from now.

Once that baseline exists, the next question gets sharper: which seemingly small config surfaces are already expanding your boundary? MCP is the clearest example.
