Your MCP Config Is Already Part of Your Security Boundary

MCP still gets treated like developer plumbing in many organizations. That is a mistake. The moment a model-facing tool declaration can request permissions, name transports, and route actions into systems outside the editor, it has joined the boundary conversation whether security reviewed it or not.

Repo grounding

Wrkr's current repo scope includes MCP server cataloging with transport, requested permissions, trust overlay, posture notes, and saved-state projection through wrkr mcp-list. That is a useful signal because it treats MCP declarations as inventory and posture data, not as harmless editor decoration.

The operational reality

Security leaders are increasingly asked some version of the same question: what exactly can these AI assistants call? The answer often drifts immediately toward models, providers, and procurement. But the more practical answer usually sits in the config layer. MCP declarations describe which tools the agent can see, what transport they use, and what kind of permission shape they request.

That matters because a harmless-looking config file can quietly become the route by which AI tooling reaches internal systems, third-party services, or developer-local capabilities that security never modeled as part of the production-adjacent surface. By the time the issue is discovered, the organization is no longer debating a theory. It is debating an already-expanded boundary.

The anti-pattern

The anti-pattern is to treat MCP as a convenience layer that belongs entirely to the developer-experience side of the house. Under that view, security reviews the SaaS product, maybe glances at the IDE plugin, and assumes the integration details are too low-level to matter unless an incident happens later.

That assumption breaks for the same reason API gateways, CI runners, and deployment environments eventually became security topics. The abstraction is useful right until it starts carrying real authority. Once it does, the declaration surface matters. Transport matters. Trust assumptions matter. Missing parse coverage matters. None of that is exotic. It is standard boundary hygiene applied to a new path.

The better system pattern

The better pattern is to treat MCP declarations as boundary metadata. That means inventorying them, classifying them, and reviewing them in the same posture program that already covers repos, workflows, and access inheritance. A strong inventory should tell you at least four things: which servers are declared, how they are reached, what they appear to request, and how trustworthy the declaration looks from a supply-chain perspective.

That is where Wrkr's posture framing is useful. It does not pretend to solve runtime enforcement from static inventory. It does something earlier and necessary. It makes the declaration layer visible enough that the organization can decide which paths deserve stricter runtime control later.

This is also a better way to talk to engineering. "Security wants to review every MCP config" sounds like drag. "We need a consistent view of which declared tool paths already expand the agent boundary" sounds like system design, because it is.

Why security cares

An unreviewed MCP declaration is risky for the same reason any hidden tool path is risky: it creates capability without governance memory. If there is no durable record of what was declared, what permissions were implied, and whether the path was approved, every later question gets harder. That includes internal review, external audit, and plain old incident response.

For AppSec specifically, MCP also creates a new location where policy intent and supply-chain trust intersect. A declaration can look simple while still inheriting risk from packaging, pinning, endpoint trust, or surrounding tool access. Security needs the declaration in view before it can make a mature judgment.

Why platform and engineering care

Platform teams benefit because MCP drift is an operability problem as much as a security problem. Engineers lose confidence when local and shared tool boundaries differ invisibly across machines, repos, and environments. A structured inventory reduces that uncertainty and makes later debugging less political.

It also clarifies the split between discovery and runtime control. Discovery tells you which declared edges exist. Later enforcement can decide which ones may execute under what policy. Keeping those layers separate is healthier than pretending a config review alone solves the execution problem.

Practical next step

  • Collect MCP declarations from one representative engineering group rather than discussing the topic abstractly.
  • Record transport type, requested permissions, package or endpoint trust assumptions, and parse failures.
  • Separate approved declarations from declarations security has never reviewed.
  • Decide which declaration patterns need runtime enforcement later and which just need visibility.
  • Make the resulting inventory part of the same review surface as repo and CI posture.

Once MCP enters the same posture map as the rest of software delivery, another blind spot becomes harder to ignore: unattended execution in CI.
